# خطة LinkPharma v37 — مزامنة أقل واستيراد وعناوين أدق

## الهدف والسياق
تنفيذ طلب المستخدم داخل مجلد `v37` فقط مع إبقاء `v35` والنسخ المنشورة الأخرى دون تغيير. يعاد استخدام React/TypeScript/Firestore والتصميم العربي RTL وخط Cairo والألوان الحالية. لا تُنفذ أي كتابة اختبارية على قاعدة Firestore الحية؛ اختبارات الصلاحيات تعمل على Emulator.

## النهج

1. **تقليل قراءات Firestore:** الاستفادة من `persistentLocalCache` الموجود وإنشاء طبقة مزامنة مشتركة لمجموعات الكتالوج تستقبل `onSnapshot` وتطبق `docChanges()` على ذاكرة واحدة. أول مزامنة لكل جهاز/استعلام تجلب مجموعة النتيجة، وبعدها تُطبّق الإضافات والتعديلات والحذوفات الواردة عبر listener بدلاً من استعلام كامل متكرر أثناء اتصال الجلسة. أسعار الموردين تظل مقيدة بمورد/أصناف/صلاحيات المستخدم. نعرض حالة اتصال واضحة ولا نستعمل localStorage غير المقيّد كبديل بعد خطأ صلاحية. لا ندّعي أن أول تحميل لجهاز جديد أو فقد cache مجاني.

2. **استيراد الأسعار:** إضافة تحرير صف Excel قبل المطابقة، ومحدد للصنف الموجود قابل للبحث، ومحرر للصنف المرتبط. تحفظ أسماء الملف البديلة بشكل دائم مرتبطة بالمورد والصنف وحقول الهوية. يطبق الربط الآلي فقط للتطابق الفريد والمتوافق في التركيز والشكل والعبوة والشركة والباركود؛ التعارض يبقى للمراجعة اليدوية. تعديل الصنف لا يغيّر `productId` أو يخلط سجل الأسعار التاريخي بصمت.

3. **المناطق والفروع:** استبدال JSON في لوحة الإدارة بمحرر هرمي للمحافظات والمدن والشوارع. يدعم حساب الصيدلية عدة فروع، لكل فرع موقع من القاموس وعنوان تفصيلي ورقم تواصل، مع فرع افتراضي واختيار الفرع عند الطلب. تكون حقول الموقع والعنوان التفصيلي إلزامية للصيدلية عند إكمال الملف أو إضافة/تعديل فرع. تُقرأ بيانات `gazaLocations` والعناوين القديمة للتوافق أثناء الانتقال.

4. **توصيل المستودعات:** اختيار محافظة كاملة أو مدينة/شارع من قاموس المواقع عند تعيين أيام التوزيع. الأولوية: شارع محدد ثم مدينة ثم محافظة ثم إعداد عام. لا تتغير صلاحيات الإدارة أو المندوب المفوض لمستودعه.

5. **القواعد والتحقق والنشر:** تحديث الأنواع والخدمات وقواعد Firestore واختبارات Emulator، ثم فحص TypeScript والبناء والفرق. تنشر v37 بعد نجاح الفحوص. قواعد Firestore منفصلة عن GitHub Pages؛ تتطلب صلاحية Firebase مستقلة لتفعيلها على قاعدة الإنتاج.

## هيكل المشروع المعني
- `src/services/dataStorage.ts`, `src/firebase.ts`: التخزين والمزامنة وقراءات/كتابات Firestore.
- `src/services/import.ts`, `src/utils/fuzzyMatch.ts`, `src/utils/productCatalog.ts`: قراءة الصفوف وتطبيعها وهوية الصنف والأسماء البديلة.
- `src/pages/admin/ImportPrices.tsx`, `src/pages/admin/Products.tsx`, `src/components/SearchSelect.tsx`: تحرير الصف والبحث والمطابقة والتحرير.
- `src/pages/admin/ControlCenter.tsx`, `src/utils/gaza.ts`, `src/pages/admin/V18Operations.tsx`: إدارة المواقع وجدول التوصيل.
- `src/pages/auth`, `src/pages/pharmacy/ProfileEdit.tsx`, `Profile.tsx`, `Cart.tsx`: ملف الصيدلية والفروع واختيار فرع الطلب.
- `src/types/index.ts`, `firestore.rules`, `test/firestore-v25.rules.test.ts`: نموذج البيانات والصلاحيات والاختبارات.

## قرارات السلامة
- أسماء الموردين البديلة لا تنشئ أصنافاً مكررة ولا تغير المعرف المعتمد؛ يحسم التباس الهوية بمراجعة يدوية.
- الصنف المتغير يبقى له `productId` نفسه فقط عند ثبات الهوية؛ تغيير التركيز/الشكل/العبوة قد يتطلب صنفاً منفصلاً.
- تحفظ الفروع مع معرّفات المحافظة/المدينة/الشارع ووصف العنوان، لا كنص مركب فقط.
- لا يُعلن نجاح حفظ الإنتاج إلا بعد نجاح Firestore؛ ويُختبر مسار الرفض وعدم الوصول في Emulator.

## v39 — Subscription Experience Studio

تم اختيار اتجاه بصري بعنوان **Pharmacy Signal Glass**: واجهة عربية هادئة بعمق زجاجي، أخضر طبي مملوك للعلامة، وحركة خفيفة تعطي إحساساً بالثقة دون إرباك الاستخدام على الهاتف.

- **الحركة والعمق:** بطاقات المعاينة واللمسات ثلاثية الأبعاد خفيفة، مع احترام `prefers-reduced-motion`.
- **التجربة:** صفحة إدارة واحدة تقسم العمل إلى حالة العميل، النصوص، الباقات، والمعاينة.
- **الهوية:** أخضر Link Pharma مع خلفيات نعناعية، حواف كبيرة، أزرار بارتفاع لمس مناسب، وتصميم متجاوب يبدأ من الهاتف.
- **التنفيذ:** `src/services/subscriptionPolicies.ts` يحوي نموذج السياسات والافتراضات والتخزين، و`src/pages/admin/SubscriptionPolicies.tsx` يحوي محرر الإدارة والمعاينة، بينما تقرأ `SubscriptionExpiredScreen.tsx` السياسة وتعرضها للعملاء.


## v42 — Firebase Catalog Snapshots

الهدف هو تقليل قراءات Firestore من دون Google Sheets أو خدمة خارجية، مع إبقاء Firebase المصدر الوحيد للمنتجات والأسعار.

- تُحفظ المنتجات والأسعار الأصلية في مجموعات Firebase الحالية.
- بعد استيراد الأسعار أو الكتالوج، يعيد النظام بناء نسخة versioned مجمعة في `catalog_meta/current` و`catalog_snapshots/*`.
- تقسم المنتجات والأسعار إلى أجزاء صغيرة، وكل جزء يحتوي صفوفاً متعددة بدلاً من مستند لكل صف في مسار العرض.
- صفحة أسعار الصيدلية تقرأ Snapshot المنتجات مع كاش محلي، بينما يظل تحقق سعر الصنف عند واتساب قراءة مباشرة للأسعار المطلوبة فقط.
- السلة تستخدم Snapshot الأسعار للتحميل العام عند توفره، ولا تعتبره بديلاً عن التحقق المباشر عند الإرسال.
- صلاحيات Snapshot: المدير يكتب، المستخدم المسجل يقرأ Snapshot المنتجات، والصيدلية ذات الاشتراك الفعال تقرأ Snapshot أسعار مستودعاتها المسموحة فقط.
- لا يستخدم التطبيق Google Sheets ولا يضع مفاتيح خارجية في الواجهة.

الملفات الأساسية هي `src/services/dataStorage.ts` لبناء النسخ وقراءتها والكاش وربط الاستيراد، و`src/pages/pharmacy/Prices.tsx` و`Cart.tsx` لاستخدام Snapshot مع fallback آمن، و`src/pages/admin/CatalogSnapshots.tsx` لإعادة البناء اليدوي، إضافة إلى `firestore.rules` للصلاحيات. يستمر اتجاه Pharmacy Signal Glass بواجهة هاتفية أولاً وبدون زخارف زائدة في أداة تشغيلية.

النسخة المجمعة تستهدف نحو 180 صفاً لكل مستند، وتكتب على دفعات أقل من حدود Firestore. لا تُحذف النسخ السابقة تلقائياً. إذا فشل بناء Snapshot لا يفشل حفظ الاستيراد الأساسي؛ يعود التطبيق للقراءة الأصلية.
